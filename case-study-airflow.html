Project Overview

A production-ready data scraping pipeline built with Apache Airflow 2.10.5, demonstrating modern data engineering practices for building reliable, maintainable ETL workflows. The project showcases orchestration patterns, error handling strategies, and idempotent data operations.

What I Built: A fully containerized pipeline that scrapes web data, validates it with Pydantic schemas, and persists to PostgreSQL using SQLAlchemy ORM with UPSERT logic to prevent duplicates.

System Architecture

The pipeline follows a five-stage workflow orchestrated by Airflow: Database Initialization → Scraping → Transformation → Persistence → Reporting. Each task can be retried independently if it fails.

Verified Implementation Details

✅ What's Actually Implemented

Airflow DAG with Task Dependencies
File: dags/scraping_pipeline_dag.py (232 lines)

The DAG defines 5 tasks with explicit dependencies using the >> operator. Configured with retries=3, retry_delay=5 minutes, and execution_timeout=1 hour. Scheduled daily at 2 AM UTC with catchup=False to prevent backfill on first deployment.

Tasks communicate via XCom (xcom_push/xcom_pull) to pass scraped data between stages.
Idempotent UPSERT Operations
File: src/persistence.py (131 lines)

Uses PostgreSQL's INSERT ... ON CONFLICT DO UPDATE via SQLAlchemy's insert().on_conflict_do_update(). The article_url field serves as the unique constraint. If a duplicate is detected, the record is updated instead of causing an error.

This makes the pipeline safe to run multiple times on the same data without creating duplicates or failing.
Data Validation with Pydantic
File: src/transformer.py (137 lines)

The ArticleData Pydantic model validates scraped data before database insertion. Enforces required fields (article_url, source_url, title, content) and validates content length constraints.

Invalid articles are logged and skipped rather than crashing the pipeline.
Comprehensive Test Suite
Files: tests/test_scraper.py (207 lines), tests/test_transformer.py (274 lines)

Unit tests cover scraper retry logic, fetch failures, transformation validation, and database operations. Uses pytest with mock objects to avoid hitting real websites during testing.

Tests verify idempotent behavior by running operations multiple times and checking for consistent results.
Docker Containerization
Files: Dockerfile, docker-compose.yaml

Custom Airflow image based on apache/airflow:2.10.5-python3.11. Docker Compose orchestrates Airflow webserver, scheduler, worker, PostgreSQL, and Redis. All dependencies pinned in requirements.txt.

Environment variables configured via .env file for portability across development and production environments.

Engineering Decisions

  • Why Airflow? Provides DAG visualization, built-in retry logic, scheduling, monitoring UI, and backfill capabilities — features that would require significant custom development with alternatives like cron jobs.
  • Idempotency by Design: Used PostgreSQL UPSERT operations and timestamp-based deduplication. This allows safe retries, manual reruns, and backfilling without data corruption.
  • Fail Gracefully: Each scraping source is wrapped in try-except blocks. If one source fails, the pipeline continues with others and logs the error rather than crashing the entire DAG.
  • Configuration as Code: All settings (database URLs, scrape targets, rate limits) managed via environment variables and Pydantic settings. No hardcoded values in the source code.
  • Testing Strategy: Used mocks to avoid hitting real websites during tests. Verified retry logic, validation behavior, and UPSERT operations with test databases.

What I Learned

  • Start Simple, Add Complexity Later: The first version had a basic DAG with minimal error handling. I added retry logic, validation, and monitoring incrementally based on what broke in testing.
  • Observability is Critical: Airflow's UI makes debugging significantly easier. Being able to see which task failed, read logs, and inspect XCom data saved countless hours.
  • Test the Failure Paths: The most valuable tests were the ones that simulated failures (network timeout, invalid data, database unavailable). That's where bugs hide.
  • Idempotency Takes Effort: Making operations truly idempotent requires careful thinking about state, timestamps, and unique constraints. But it's worth it for operational safety.
